Over the past few days, the most ordinary tools in a developer's daily life were all hit: the SSH server, CI, Git, the Node.js runtime and the Apache web server. What these flaws share is low-level details that look harmless on their own but end up opening the door.

## SSHole: an overly long password opened SSH on Alpine Linux

OpenSSH 10.6p2 shipped as an emergency release on November 5 to fix "SSHole" (CVE-2026-123158), found by Özgün Kültekin. The bug chains three behaviours that are each correct on their own. An account with no password stores `*` instead of a hash. So that response timing does not reveal whether an account exists, sshd still computes a hash using another account's salt, a protection dating back to 2016. Finally, the `crypt()` function in musl, Alpine's C library, returns `*` as an error signal when given more than 256 bytes. With a password between 257 and 1,024 characters, sshd ends up comparing `*` to `*`, and access is granted.

The flaw is being exploited. According to [The Hacker News](https://thehackernews.com/2026/11/hackers-exploited-openssh-sshole-flaw.html), Previdian saw a full root takeover of a honeypot less than 9 hours after the CVE was published. Systems built on glibc, setups using PAM, Dropbear and cloud-init images are not affected. Alpine is fixed in 3.21.10, 3.22.8, 3.23.8 and 3.24.4, and sshd must be restarted afterwards. According to the [OpenSSH release notes](https://www.openssh.org/releasenotes.html), the fix is a workaround that rejects stored hashes shorter than 4 characters. The root cause remains in musl. Severity is also debated: NIST rates it 8.1 out of 10, while OpenSSH calls it critical ([Next](https://next.ink/266066/une-faille-dans-alpine-linux-permet-de-se-connecter-avec-un-mot-de-passe-trop-long/)).

## "wfx": thousands of GitHub accounts steal CI secrets

Since November 10, a campaign has been using compromised GitHub accounts to target GitHub Actions workflows. According to [Aikido](https://www.aikido.dev/blog/compromised-github-accounts-push-ci-secret-stealer-to-tens-of-thousands-of-repositories), 4,837 accounts opened pull requests titled "docs: dependency audit notes" in 61,764 repositories, and at least 1,806 repositories ran the malicious code. [SafeDep](https://safedep.io/blog/github-actions-wfx-credential-stealer) counts 8,093 modified repositories: 7,309 through an existing workflow, 771 through a `postinstall` script that also runs on developers' machines, and 16 through a new workflow. The script steals GitHub secrets, AWS, Google Cloud, Azure, npm, PyPI and SSH credentials, as well as AI API keys. It then erases its traces in about a minute. These figures are lower bounds, since only public repositories are visible.

Recommended defences include two-factor authentication, short-lived tokens with narrow permissions, and `npm install --ignore-scripts` for unfamiliar projects. GitHub now also offers a lock file for actions, the equivalent of `package-lock.json`: tags stay readable, but the code that runs is pinned. Hugo van Kemenade [explains how to set it up](https://hugovk.dev/blog/2026/lock-github-actions/).

## Git 2.56.1 and Node.js: updates to apply

On November 10, [Git 2.56.1](https://github.blog/open-source/git/git-security-vulnerabilities-announced-7/) fixed six vulnerabilities. The most serious one allowed code execution during a `git clone --recursive`: an extremely long path passed the safety check and was then truncated into a sensitive name such as `.git`. Older branches are patched too. Copies of Git bundled inside other tools need updating as well.

On November 11, [Node.js](https://nodejs.org/en/blog/vulnerability/november-2026-security-releases) released 22.23.5, 24.22.3 and 26.13.1, fixing 16 vulnerabilities, 7 of them severe. Over HTTPS, calling `res.flushHeaders()` and then `res.end()` with data could send fragments of server memory back to the client, including the TLS private key. Several of these flaws were found by AI-assisted researchers. Unsupported versions remain vulnerable.

## Apache HTTP Server: a race condition in HTTP/2

[Wiz](https://www.wiz.io/blog/cve-2026-119618-rce-apache-http-server-vulnerability) describes a race condition in the HTTP/2 module of Apache HTTP Server, versions 2.4.55 to 2.4.70. It could allow unauthenticated remote code execution. It is fixed in 2.4.71, and no exploitation is known so far. This information comes from a single source.

## Analysis

These incidents share a common thread: implicit assumptions between components. In SSHole, an error sentinel value, `*`, is mistaken for valid data. In Git, truncation happens after validation. In Apache, two threads touch shared state. For C developers the lesson is a familiar one, but its cost has rarely been this visible: an error value must never be able to look like normal data, and input must be validated in the exact form in which it will be used.

For TypeScript and Node.js developers, the priority is the supply chain: pin CI actions, limit the scope of secrets, be wary of `postinstall` scripts and follow the Node.js security release schedule. A Fastify API such as the one behind [NEXUS](/nexus) depends directly on that runtime, so fixes of this kind affect every application of that type. Race conditions like Apache's also echo the concurrency fundamentals covered in the École 42 [Philosophers](https://github.com/M-Jorda/philosophers) project, which is built on pthreads and mutexes. Worth watching in the coming weeks: a root-cause fix in musl, and the still-unknown origin of the compromised GitHub accounts.
