Ces derniers jours, les outils les plus ordinaires du quotidien d'un développeur ont tous été touchés : le serveur SSH, la CI, Git, le runtime Node.js et le serveur web Apache. Point commun : des détails de bas niveau, souvent anodins pris isolément, qui finissent par ouvrir la porte.

## SSHole : un mot de passe trop long ouvrait SSH sur Alpine Linux

OpenSSH 10.6p2 est sortie en urgence le 5 novembre pour corriger « SSHole » (CVE-2026-123158), découverte par Özgün Kültekin. Le mécanisme enchaîne trois comportements corrects pris un par un. Un compte sans mot de passe stocke `*` à la place de l'empreinte. Pour ne pas révéler l'existence d'un compte par le temps de réponse, sshd calcule tout de même une empreinte avec le sel d'un autre compte, une protection qui date de 2016. Enfin, la fonction `crypt()` de musl, la bibliothèque C d'Alpine, renvoie `*` comme signal d'erreur au-delà de 256 octets. Avec un mot de passe de 257 à 1 024 caractères, sshd compare donc `*` à `*`, et l'accès est accordé.

La faille est exploitée : selon [The Hacker News](https://thehackernews.com/2026/11/hackers-exploited-openssh-sshole-flaw.html), la société Previdian a observé une prise de contrôle root d'un pot de miel moins de 9 heures après la publication de la CVE. Les systèmes basés sur glibc, ceux qui passent par PAM, Dropbear et les images configurées par cloud-init ne sont pas concernés. Alpine est corrigée en 3.21.10, 3.22.8, 3.23.8 et 3.24.4, et sshd doit être redémarré. D'après les [notes de version OpenSSH](https://www.openssh.org/releasenotes.html), le correctif est un contournement qui refuse les empreintes de moins de 4 caractères. La cause profonde reste dans musl. La gravité est d'ailleurs discutée : 8,1 sur 10 pour le NIST, faille critique pour OpenSSH ([Next](https://next.ink/266066/une-faille-dans-alpine-linux-permet-de-se-connecter-avec-un-mot-de-passe-trop-long/)).

## « wfx » : des milliers de comptes GitHub volent les secrets de la CI

Depuis le 10 novembre, une campagne utilise des comptes GitHub compromis pour viser les workflows GitHub Actions. Selon [Aikido](https://www.aikido.dev/blog/compromised-github-accounts-push-ci-secret-stealer-to-tens-of-thousands-of-repositories), 4 837 comptes ont ouvert des pull requests intitulées « docs: dependency audit notes » dans 61 764 dépôts, et au moins 1 806 dépôts ont exécuté le code malveillant. [SafeDep](https://safedep.io/blog/github-actions-wfx-credential-stealer) compte 8 093 dépôts modifiés : 7 309 via un workflow existant, 771 via un script `postinstall` qui s'exécute aussi sur les postes des développeurs, et 16 via un nouveau workflow. Le script vole les secrets GitHub, les identifiants AWS, Google Cloud, Azure, npm, PyPI et SSH, ainsi que des clés d'API d'IA. Il efface ensuite ses traces en une minute environ. Ces chiffres sont des minimums, puisque seuls les dépôts publics sont visibles.

Parmi les parades citées : la double authentification, des jetons à droits limités et de courte durée, et `npm install --ignore-scripts` pour un projet inconnu. GitHub propose aussi désormais un fichier de verrouillage des actions, l'équivalent de `package-lock.json` : les tags restent lisibles mais le code exécuté est figé. Hugo van Kemenade [en détaille la mise en place](https://hugovk.dev/blog/2026/lock-github-actions/).

## Git 2.56.1 et Node.js : des mises à jour à appliquer

Le 10 novembre, [Git 2.56.1](https://github.blog/open-source/git/git-security-vulnerabilities-announced-7/) a corrigé six failles. La plus grave permettait d'exécuter du code lors d'un `git clone --recursive` : un chemin extrêmement long passait le contrôle de sécurité, puis était tronqué en un nom sensible comme `.git`. Les anciennes branches sont aussi corrigées. Les copies de Git intégrées à d'autres outils doivent elles aussi être mises à jour.

Le 11 novembre, [Node.js](https://nodejs.org/en/blog/vulnerability/november-2026-security-releases) a publié les versions 22.23.5, 24.22.3 et 26.13.1, qui corrigent 16 failles, dont 7 graves. En HTTPS, appeler `res.flushHeaders()` puis `res.end()` avec des données pouvait renvoyer au client des fragments de mémoire du serveur, y compris la clé privée TLS. Plusieurs de ces failles ont été trouvées par des chercheurs assistés par IA. Les versions qui ne sont plus maintenues restent vulnérables.

## Apache HTTP Server : une course critique dans HTTP/2

[Wiz](https://www.wiz.io/blog/cve-2026-119618-rce-apache-http-server-vulnerability) décrit une race condition dans le module HTTP/2 d'Apache HTTP Server, des versions 2.4.55 à 2.4.70. Elle permettrait d'exécuter du code à distance sans authentification. La faille est corrigée en 2.4.71 et aucune exploitation n'est connue à ce stade. Ces informations viennent d'une source unique.

## Analyse

Ces incidents ont un point commun : des hypothèses implicites entre composants. Avec SSHole, une valeur sentinelle d'erreur, `*`, se confond avec une donnée valide. Dans Git, une troncature intervient après la validation. Avec Apache, deux threads accèdent à un état partagé. Pour un développeur C, la leçon est classique, mais le prix a rarement été aussi visible : une valeur d'erreur ne doit jamais pouvoir ressembler à une donnée normale, et une donnée doit être validée sous la forme exacte où elle sera utilisée.

Pour un développeur TypeScript ou Node.js, la priorité est la chaîne d'approvisionnement : verrouiller les actions de CI, limiter la portée des secrets, se méfier des scripts `postinstall` et suivre le calendrier de sécurité de Node.js. Une API Fastify comme celle de [NEXUS](/nexus) dépend directement de ce runtime : ce type de correctif concerne donc toutes les applications de cette famille. Les courses critiques comme celle d'Apache rappellent enfin les bases de la concurrence travaillées dans le projet [Philosophers](https://github.com/M-Jorda/philosophers) de l'École 42, qui repose sur les pthreads et les mutex. À surveiller dans les semaines à venir : une correction de fond dans musl, et l'origine encore inconnue des comptes GitHub compromis.
